# Application 1〜3 実装結果

## 実装
- FastAPI で画面と API を配信。UI は HTML/CSS/JavaScript とローカル Lucide。
- 要求入力、Office/PDF/テキスト添付、構造化抽出、変更前後・出典・不明点の編集。
- 確定後に変更ごとに KB 文書検索・Markdown 全文取得、Decision-1 評価、最上位1件の自動選定。
- 同一文書の変更を集約し、修正文全文と適用変更IDを生成。差分は difflib で計算。
- 候補・必要性・選定結果、原文/修正文/差分、ローカルダウンロードを表示。
- SQLite とランダムIDの添付原本保存、履歴、版管理、削除、進捗、再実行。
- 再起動時の中断検出、成功済み工程の再利用、二重実行防止。
- 上限・タイムアウト・再試行、同一オリジンと Host の制限、HTML のテキスト描画。
- 環境別設定は TOML サンプルを提供し、実体・保存データを Git 管理対象外とした。

## 確認した契約
- exmgai 0.0.9 の AsyncClient、chat.create(response_format=...)、decision.system_one を使用。
- typesafe-sdk の公開 Noul / NoulAnswer を利用。answers['needs_modification'].noul が必要性確率。
- 確率の不正値・NaN・欠落を拒否。必要性と KB の max_score は混同しない。
- KB の POST /api/search_documents、POST /api/download_document を利用。text/base64 の両取得形式を検証。
- exmgai の標準添付パーサーは PDF のみのため、Office はアプリ側で抽出。

## 検証結果
- pytest: 48件成功。添付形式、空・暗号化PDF、形式不一致、Excel巨大範囲、入力上限、SDK回答、AI再試行、トークン上限、KB契約、版競合、評価不完了、文書集約、差分、再実行・中断復元、API・配信を検証。
- Flake8: 最大120文字のルールで成功。
- node --check: JavaScript の構文検証に成功。
- VS Code の src/tests 診断: エラーなし。
- ブラウザ（通常サーバー）: 初期表示、案件保存、AI未設定の失敗表示、案件削除を確認。
- ブラウザ（テスト用AI/KBサーバー）: 入力→抽出→2件に編集→自動生成→1文書に集約→原文・修正文・差分切替、必要性と選定結果、ダウンロードリンクを確認。
- デスクトップ1365pxとモバイル390pxで表示と横方向のはみ出しを確認。Lucideの描画を確認。
- モバイルの案件メニューから履歴を再読込みし、矢印キーの文書タブ切替を確認。
- 長い文書名・説明でも横方向のはみ出しなし。HTMLタグ入りの原文が文字列として表示され、img/script要素が生成されないことを確認。

## 検証で修正した事項
- Windows で pytest 実行ファイルの起動が拒否されたため、uv run python -m pytest を標準の検証コマンドにした。
- SQLite 書込み中のキャンセルにより、遅れた書込みが中断状態を上書きする競合を修正。書込み完了を待ってから中断を記録する。
- 部分成功後の再実行で、別の変更が同じ文書へ追加された場合に修正案を再生成する。
- 進捗の古い応答で、切り替え先の案件を上書きしないようにした。
- ファビコンの CSP 警告、末尾改行などの静的チェック違反を修正。

## 制限・未検証
- 実 AI・実 KB への接続は未実施。SDK型とモック契約、テスト用サービスでの結果であり、実接続成功を意味しない。

- 単一プロセス・ローカル利用専用。認証・分散ジョブ基盤は含まない。
- 再起動後は手動で再実行する。外部呼出しの厳密な一回実行は保証しない。
- OCR、図形の完全理解、旧Office、Application 4〜7 は対象外。KBや元仕様書は更新しない。
