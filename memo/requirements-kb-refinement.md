# KB-MCP を使った要求整理

## 方針と実装

- 初稿の生成時に、既存仕様で確認したい点と検索語を受け取る。アプリ側が検索範囲を管理し、検索・取得と推敲を最大3ラウンド行う。整理用の仕様候補は、ユーザー確認後の仕様書特定には引き継がない。
- 根拠の文書名と位置は、実際にモデルへ渡した抜粋の ID から付与する。現行仕様は変更前・用語・責務の裏付けに使い、変更後は依頼内容を根拠にする。KB 障害などで確認できない場合は暫定表示とする。
- マスキング API には Markdown 全文を1文書ずつ送り、他の入力とはアプリ側で結合する。伏せ字を衝突しないように揃え、対応表はモデルに渡さない。実行内の再利用とサーバー側の検出キャッシュを使い分ける。
- 生成 AI と Decision-1 の推定費用は `env.toml` のモデル別単価から算出し、実行終了時だけ JSON で標準出力に記録する。別サービスの検出用 LLM は含まない。

## 検証

- 最大3ラウンド、検索の重複排除、根拠 ID の検証、KB 障害時の暫定化、後続工程の独立をモックで確認。
- 仕様単体のマスク、伏せ字の衝突と復元、失敗時の未送信、モデル応答後の検証失敗時にも費用を計上することを確認。
- 本番 KB、マスキング API、モデルを使った実データでの評価は別途実施する。

## 上限の設定

要求整理のラウンド数・ラウンドごとの仕様書取得件数・実行全体の仕様書取得件数を `config.toml` で設定できる。
省略時は従来どおり3回・2件・6件。非既定値を TOML から読み込み、実行時の各上限に反映されることをテストする。
